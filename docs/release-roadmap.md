# ニゲヨのリリース実装ロードマップ

コミット `663990d` のコードと運用手順を基にした提案。ローカルでNodeの既存テスト42件とAWS関連の既存テスト7件が成功した。稼働中のAWS設定、Appleの配布設定、実機での現行版の動作は未確認。

## 現在の仕組み

- **実災害の通知**。ECS FargateがP2P地震情報の全国WebSocketを1本購読する。緊急地震速報（556）と津波予報（552）を登録地域で照合し、順序・重複・取消を判定する。端末ごとの状態と送信待ち通知をS3に保存してから、APNsに通常通知と必要に応じてLive Activityの開始・終了を送る。地震情報（551）はこの初動通知の対象外。[監視処理](../server/monitoring/service.mjs) · [AWS送信処理](../aws/regional-worker.mjs)
- **端末登録**。診断ログからAPNsトークンをコピーし、運用者がSecrets Managerの端末リストに追加する。共通設定のバリデーションは最大4台。アプリの地域設定APIは登録済みトークンを照合して購読設定をS3に保存する。公開版に必要な新規端末の自己登録は未実装。[4台の設定手順](aws-live-alerts.md) · [登録API](../aws/live-registration.mjs) · [上限の実装](../aws/apns-training/index.mjs#L44)
- **iPhoneでの体験**。ロック画面のLive Activityからガイドへ進める。壁紙切り替えは、利用者がインポート・設定するiOSショートカットに依存する。避難先と通知対象地域は設定でき、避難場所データはアプリに同梱されている。[iOSの設定手順](setup.md) · [ショートカット](shortcuts.md) · [地域データ](notification-region-data.md)
- **運用画面**。PC向けのWeb画面はペアリングした端末へのデモ操作用。AWSの訓練配信は別のLambdaをIAM権限で起動する。実配信や障害を横断して見る管理画面は見当たらない。[デモサーバー](../server/demo/server.mjs) · [AWS訓練配信](aws-training-push.md)

## P0 · 公開前に必要

| 作業 | 現状 | どう変えるか |
| --- | --- | --- |
| 01. アプリから端末を自己登録 | 運用者が端末トークンを手で登録。最大4台。 | 通知を有効にした利用者をアプリから登録。公開版は利用者ログインなしを初期案とし、サーバーがインストール単位の資格情報を発行する。同じ端末から再送しても登録は増えない。 |
| 02. 通知先と認証を分離 | APNsトークンが設定APIのBearer認証にも使われる。 | 通知先トークンと設定更新用の資格情報を分離する。iOSでは資格情報をKeychainに保存し、設定変更・購読解除はそのインストールに限定。登録レート制限も同時に整える。 |
| 03. トークン更新と失効 | トークン更新を端末の許可リストに自動反映する経路がない。送信側はHTTPステータス中心。 | 起動時にAPNsから取得し直し、同一インストールの通知先を更新。通常・Activity開始・Activity更新トークンを別々に管理。失効応答で該当トークンを停止し、更新直後の有効なトークンは残す。 |
| 04. 設定が反映されたことを表示 | 設定を送信できるが、許可・サーバー反映・ロック画面設定は別の状態。 | 「通知許可」「地域設定を同期済み」「ロック画面設定」を個別に表示。オフライン保存や失敗時は未反映として見せ、再接続で同期する。 |
| 05. 購読解除・データ削除 | 設定無効化と端末内リセットがあり、サーバー側はデモ用の保存構成。 | 通知オフ、OS権限変更の検知、登録削除を設計。配信直前に有効状態を再確認し、登録情報・トークン・ログの削除や保持期限を決める。 |
| 06. 端末と地域をデータベースへ | 端末はSecrets Manager、購読はS3。ワーカーは端末ごとに設定を約3秒間隔で確認する。 | 端末・購読・APNsキーを分離。DynamoDBを候補に「災害種別＋区域ID」から対象端末を引けるようにする。登録・変更の直後に古い設定で誤送信しないよう、送信直前に最新状態を確認する。 |
| 07. 監視と配信を分離 | 単一の監視タスクが全端末の照合を行い、S3の状態ファイル全体を書き替える。 | 受信・災害状態の更新・対象検索・APNs送信を分離。確定した配信対象をSQSなどに積み、送信処理を並列化する。中断時に配信ジョブを復元できるよう状態保存とジョブ作成のつなぎも設計する。 |
| 08. 期限・取消・重複の保証範囲 | 2分の期限と保留管理があり、APNs受付から保存までの障害で再送しうる。 | イベントID・更新番号・インストールID・配信種別で重複を抑え、期限切れや取消前の古いジョブを送信直前に止める。訓練で順序逆転、再起動、再試行を検証する。 |
| 09. APNs送信の効率と失敗分類 | リクエストごとにHTTP/2接続を開く。多くの4xxを処理済みとして扱う。 | 接続を再利用し、同時送信の上限を設ける。失効・署名設定不良・送信過多・一時障害を区別。期限内だけバックオフ再試行し、署名異常は運用者に通知する。 |
| 10. 情報源と監視の可用性 | ECSは1タスク・1サブネット。切断中の警報を取り直す機能はない。 | 配信元の利用条件と切断時に回復できる範囲を確認。複数AZでの待機系と単一の有効な受信処理、切断検知、切替訓練を設計し、復旧時の古い警報は期限で制御する。 |
| 11. 管理画面の最小版 | デモ画面とLambda操作が分かれている。 | 運用者専用画面で、フィード接続状態、最新イベント、地域別購読数、送信待ち件数、APNs受付・失敗件数、訓練履歴を確認できるようにする。APNs受付と実機の表示確認は別の指標にする。 |
| 12. 安全な訓練送信と停止操作 | IAMで訓練Lambdaを起動。本番監視にもスタックの有効化フラグがある。 | 閲覧と操作を権限分離。専用テスト端末・訓練ラベル・送信前の対象確認・操作履歴を用意。本番配信の停止と再開は監査し、停止中の期限切れジョブは破棄する。 |
| 13. 監視・オンコール・対応手順 | CloudWatchに主にログを出している。 | フィード切断、受信からAPNs受付までの遅延、キュー滞留、失敗率を可視化。閾値・通知先・初動手順を決め、実機の定期訓練で検知を確認する。 |
| 14. 通常通知とLive Activityの実機検証 | 2経路で送られ、壁紙変更には通常通知を使う。検証手順はある。 | ロック、バックグラウンド、低電力、権限オフ、圏外復帰、取消・引き下げを対象にする。二重鳴動とガイドの二重起動も確認する。壁紙未設定でも通常通知から行動案内に進めるようにする。 |
| 15. 本番・検証環境と配布設定 | 登録APIのホストや署名はローカル設定で差し替える構成。 | 検証と本番で登録先・認証情報・送信対象を分離し、署名付きビルドで設定を検査。TestFlightから公開版までの手順、プライバシー説明、問い合わせ導線を整える。 |
| 16. 負荷試験と公開基準 | デモの動作確認が中心。公開時の想定容量は未確認。 | 同一地域に通知が集中する試験と、登録の集中・複数地域イベント・APNs障害を組み合わせた試験を用意。対象外への誤送信、期限超過、配信遅延、コストを広げる前に測る。 |
| 17. 通知・ガイドの内容確認 | 地震、津波、訓練の表示と多言語素材がある。 | 警報・注意報・取消の見分けやすさ、通知に出す情報源、地震と津波が重なる場面をレビューする。日本語・英語・韓国語で実機確認し、公式情報へすぐ移れるようにする。 |

## 最初の実装の区切り

**端末の自己登録からテスト通知までを縦に通す。** インストール単位の認証、APNsトークン同期、地域の登録・変更・解除、設定画面の受信状態をつなぐ。検証環境で5台目以降が運用者の作業なしに登録でき、同じ地域で訓練しても対象外と解除済みの端末には配信されないことを確認する。旧4台の訓練経路は移行中の比較に使う。

続いて地域から対象を引く配信経路と管理画面の閲覧機能をつなぐ。限定公開では実機確認と負荷試験の結果から対象地域・人数を決め、広げるたびに配信遅延と失敗率を確認する。

関連仕様は[AppleのAPNs登録](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns)、[APNsの応答処理](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns)、[AWSのSQS再試行と部分失敗](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-errorhandling.html)、[P2P地震情報のJSON API v2](https://www.p2pquake.net/develop/json_api_v2/)を参照。
